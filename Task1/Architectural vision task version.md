
# 1 Бизнес-контекст и цели
## 1.1 Задача 
Основная задача решения: организовать цифровой канал сбыта для «Diamond Universe». 
Решение позволит не останавливать деятельность компании во времена локдаунов, а также поможет привлечь новых клиентов и расширить возможности сбыта за счет привлечения клиентов, не имеющих возможности присутствовать при проведении аукционов.
Одновременно данное решение позволит упростить процесс закупки алмазов уже имеющимся клиентам сделать его еще удобнее и прозрачнее для клиентов.

## 1.2 Контекст
Задача по разработке данного решения возникла после введения ограничений в связи с пандемией и невозможностью в пандемию проводить аукционы в офлайн режиме.

## 1.3 Описание оптимального решения
Для выработки оптимального решения необходимо учитывать специфику имеющегося архитектурного ландшафта. В нашем случае, мы имеем несколько ИСов, практически не связанные между собой и выполняющие только малую часть необходимых для онлайн аукционов функций. Необходимо связать ИСы между собой и доработать их функциональность до возможности проводить онлайн аукционы. При этом, желательно свести к минимуму зависимости ИСов друг от друга, исключить потерю данных, снизить до минимума доработки и уменьшить риски потери данных при недоступности одной из ИСов.
Всем этим требованиям удовлетворяет подход, при котором используется брокер сообщений. Такой подход сделает ИСы независимыми друг от друга и гарантирует передачу данных между ними при временной недоступности одной из ИС.
Использование такого подхода позволит плавно переводить на брокер сообщений ИСы, не парализуя текущую функциональность. Чтобы исключить несанкционированное чтение сообщений в брокере, для каждой ИС будет использован отдельный ключ шифрования с его регулярным обновлением, который будет известен только контактирующим ИСам. Таким образом, остальные ИСы не смогут вычитывать сообщения, которые им не предназначались.
*Плюсы:*
1. Отсутствие необходимости использовать облачное хранилище и отсутствие дополнительных расходов на его оплату. Соответственно, меньше рисков во взаимодействии ИСов, в случае недоступности облачного хранилища;
2. Отсутствие необходимости настраивать прямые интеграции между ИСами, что делает сам процесс разработки более гибким и предсказуемым;
3. Мимнимальная зависимость ИСов друг от друга - в случае недоступности ИСа сообщение просто останется в очереди, процесс "не упадет";
4. Некоторое упрощение сопровождения ИСов, т.к. все файлы обмена в одном месте и легко выстроить цепочку взаимодействия и понять, на каком шаге процесс прервался.
*Минусы:*
1. Необходимо разворачивать инфраструктуру и настраивать подключение всех ИСов к брокеру сообщений; 
2. Поддержка брокера сообщений может требовать усилий со стороны команды разработки и негативно сказываться на сроках разработки в целом.


### 1.3.1 Альтернативные решения
Существует несколько вариантов альтернативного решения данной проблемы.

#### 1.3.1.1 Использование облачного хранилища
Взаимодействие ИСов, без использования очереди сообщений, с использованием облачного хранилища. В этом случае, каждая ИС выгружает результирующие файлы в облако, а следующая за ней по цепочке процесса ИС забирает этот файл из облачного хранилища и продолжает процесс.
*Плюсы:*
1. Отсутствие необходимости разворачивать брокер сообщений и настраивать с ним интеграцию ИСов.
*Минусы:*
1. Использование облачного хранилища накладывает дополнительные расходы; 
2. С облачным хранилищем есть быть ограничения по количеству хранимых файлов. Необходимо продумывать некий файловый архив и процесс архивации данных; 
3. Необходимо продумывать сложную логику в случае сбоя работы ИСа, отправки файлов или "падения" одной или нескольких ИСов, чтобы запустить процесс снова.

#### 1.3.1.2 Прямое взаимодействие ИСов
Взаимодействие ИСов, без использования очереди сообщений, без использованием облачного хранилища, передачей данных посредством API. В этом случае, каждая ИС, после выполнения своей части процесса, инициирует вызов следующей за ней по процессу ИС, и передает ей данные в виде json с данными, необходимыми для продолжения процесса.
*Плюсы:*
1. Отсутствие необходимости разворачивать брокер сообщений и настраивать с ним интеграцию ИСов.
2. Отсутствие необходимости использовать облачное хранилище и отсутствие дополнительных расходов на его оплату. Соответственно, меньше рисков во взаимодействии ИСов, в случае недоступности облачного хранилища;
*Минусы:*
1. Необходима одновременная синхронная доработка по реализации API на стороне двух ИСов, что негативно скажется на сроках реализации; 
2. В случае сбоя работы одного ИСа и "падения" процесса на стороне этого ИСа, глобальный бизнес-процесс может быть сломан полностью. Необходима дополнительная логика для обхода таких инцидентов; 
3. Изменение контракта API в начале цепочки взаимодействия ИСов может привести к необходимости синхронного изменения контрактов во всех ИСах одновременно. Аналогичная проблема может быть во всех вариантах реализации, но именно в прямом взаимодействии она может быть максимально критична, когда одно изменение контракта нужно протянуть по всей цепочке ИСов.


## 2 Реализация и сроки
### 2.1 Этапы проекта
В начале реализации проекта мы имеем несколько разрозненных ИС, не интегрированных между собой и не поддерживающих необходимую функциональность.
Для максимально быстрого старта из-за сжатых сроков вся функциональность, которая только может быть переложена на пользователей, перекладывается на исполнение вручную пользователями. Для этого нужно, чтобы ИСы поддерживали импорт и экспорт данных в/из файл/а, что в дальнейшем достаточно легко будет адаптировать для интеграции с брокером и отправкой файлов в него.
Всего получается три этапа реализации.

#### 2.1.1 I Этап
В первый этап входят все критически важные доработки, без которых невозможен запуск решения.
Весь обмен данными между ИСами осуществляется пользователями вручную посредством импорта и экспорта файлов.
Доработка ИСов:

**ИС Алмазы**: 
1. Добавление функциональности для отбора алмазов для цифрового аукциона - 0,5 спринта;
2. Добавление функциональности для выгрузки отбора алмазов в файл - 0,5 спринта;

**ИС Логистика**: 
1. Добавление функциональности для перевозки алмазов в пункты назначения - 0,5 спринта;
2. Формирование актов выполненных работ осуществляется - вручную;

**ИС Аукцион**:
1. Формирование данных для клиентов об алмазах на аукцион - вручную;
2. Публикации данных для клиентов с оцифрованными алмазами осуществляется на сайте. Заявки на аукционе принимаются вручную по телефонам и месенджерам;

**ИС Лаборатория**:
1. Добавление функциональности для импорта файла с отобранными алмазами - 1 спринт;
2. Добавление функциональности для экспорта файла с оцифрованными алмазами - 1 спринт.
*Данная функциональность не влияет на объем работ внутренней команды, так как осуществляется силами внешней команды.

При всей оптимистичности сроков планируется выделить минимум 1 спринт на дебаггинг и тестирование всей цепочки процессов.

#### 2.1.2 II Этап
На втором этапе, после того, как процесс уже запущен и работает, планируется планомерная работа по внедрению новой функциональности в ИСы, чтобы минимизировать человеческий фактор в процессе и упростить в дальнейшем обмен данными.

**ИС Логистика**: 
1. Добавление функциональности для импорта файлов с точками назначения (покупатель или лаборатория) - 1 спринт;
2. Добавление функциональности для выгрузки в файл актов выполненных работ для бухгалтерии - 1 спринт;

**ИС Аукцион**:
1. Добавление функциональности для импорта файла из лаборатории с оцифрованными алмазами - 1 спринт;
2. Добавление функциональности для публикации данных для клиентов с оцифрованными алмазами - 1 спринт;

**ИС Бухгалтерия**:
1. Добавление функциональности для импорта актов в виде файлов - 2 спринта;
2. Добавление функциональности для ведения контрактов - 2 спринта.

**ИС Лаборатория**:
1. Добавление функциональности для экспорта файла с выполненными работами по оцифровке - 1 спринт.

#### 2.1.3 III Этап
Третий этап - завершающий. На нем происходит обвязка всего имеющегося набора ИСов в единую интеграцию и максимальное исключение участия пользователей из процесса передачи данных и взаимодействия ИСов:

**Брокер сообщений**:
1. Развертывание, настройка, тестирование - 1 спринт;

**ИС Алмазы**: 
1. Подключение к брокеру сообщений (настройка, тестирование) - 1 спринт;

**ИС Логистика**: 
1. Подключение к брокеру сообщений (настройка, тестирование) - 1 спринт;

**ИС Аукцион**:
1. Подключение к брокеру сообщений (настройка, тестирование) - 1 спринт;

**ИС Лаборатория**:
1. Подключение к брокеру сообщений (настройка, тестирование) - 1 спринт;
*Данная функциональность не влияет на объем работ внутренней команды, так как осуществляется силами внешней команды.

### 2.2 Исполнители
Для реализации проекта потребуется доработка внутренних ИС компании, а также доработка ИС "Лаборатория", относящуюся к внешнему подрядчику. В связи с этим, необходимы две команды с налаженным взаимодействием: собственная (внутренняя команда) и команда подрядчика (внешняя).
