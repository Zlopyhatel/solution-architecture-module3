# 5. Стратегия отказоустойчивости и disaster recovery (disaster-recovery.md)

## 5.1. Матрица RPO / RTO по сервисам

| Сервис / База данных 				      | Целевое RPO (Потеря данных) 				      | Целевое RTO (Время восстановления) 			    | Техническая стратегия обеспечения |
| **Сервис финансов (PostgreSQL)** 	| **RPO = 0** (Потери недопустимы) 			    | **RTO < 2 минут** (Критичный простой) 		  | Синхронная репликация [TO-BE.md] + автоматический Failover (Patroni) для мгновенного переключения на реплику. Потоковая архивация WAL-логов в облачное хранилище в реальном времени. |
| **Сервис ставок (Redis)** 		    | **RPO < 5 минут** (Лимиты из Кафки) 	    | **RTO < 1 минуты** (Прямой доход бизнеса) 	| Stateless-архитектура самого сервиса. Кластер Redis с автоматическим переключением узлов. При полной потере данных кэш автоматически восстанавливается скриптом прогрева из Campaign DB и логов компактных топиков Kafka [TO-BE.md]. |
| **Сервис кампаний (PostgreSQL)** 	| **RPO < 10 минут** 						            | **RTO < 15 минут** 							            | Классическая асинхронная репликация [TO-BE.md]. Ежедневные полные бэкапы + инкрементальные бэкапы каждые 10 минут в изолированное облачное хранилище. |
| **Сервис аналитики (ClickHouse)** | **RPO < 1 часа** (Допустим гэп в логах) 	| **RTO < 2 часов** (Низкий приоритет) 			  | Шардированный кластер [TO-BE.md]. Восстановление из ежедневных бэкапов. В случае локального сбоя ClickHouse пропущенные данные за последние часы можно повторно довычитать из 3-дневного буфера Kafka. |

## 5.2. Соответствие принципам 12-факторных приложений (12-Factor Apps)

В соответствии с **Шестым фактором (Processes)** методологии 12-Factor Apps, микросервис `Binding Service` спроектирован как **Stateless-приложение** (процесс, не хранящий состояние внутри локального контейнера).

* **Механизм реализации:** Локальный диск и память контейнера используются исключительно как временный буфер для транзитных вычислений аукциона.
* Все долгоживущие данные (состояние) вынесены в специализированные внешние службы (Baking Services): оперативные лимиты — в распределенный кластер Redis,
* бизнес-конфигурации — в PostgreSQL, а логи результатов аукциона — в шину данных Apache Kafka.
* **Архитектурный эффект:** Это обеспечивает абсолютную эластичность горячего контура (Hot Path).
* Платформа AdScale способна мгновенно и горизонтально масштабироваться в облаке под любые пиковые нагрузки международного рынка (до 100 000+ RPS) путем простого тиражирования подов Binding Service.
* Процесс развертывания, уничтожения или автоматического перезапуска узлов происходит за секунды, без риска потери или повреждения бизнес-данных.
