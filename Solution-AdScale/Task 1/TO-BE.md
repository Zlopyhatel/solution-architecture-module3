# Описание целевой архитектуры платформы AdScale (TO-BE через 1 год)

## 1. Архитектурный стиль и стратегия эволюции
Для устранения проблем монолитной архитектуры (деградация в пики, блокировки БД, высокий Latency) выбран переход на **микросервисную архитектуру** 
с применением паттернов **CQRS** (Command Query Responsibility Segregation) и **Database-per-Service**.

### Стратегия миграции:
* **Отказ от Big Bang:** Переписывание системы с нуля исключено из-за высоких рисков для бизнеса и ограниченных ресурсов команды (35 человек).
* **Паттерн Strangler Fig (Финиковое дерево):** Монолит «вырезается» постепенно. Первым приоритетом выделяется самый нагруженный домен — сервис ставок.
* **Единая точка входа:** Внедряется **API Gateway**, который инкапсулирует внутреннюю структуру сети от внешних клиентов и маршрутизирует трафик.

## 2. Описание компонентов целевой архитектуры

### 2.1. Точка входа и маршрутизация (API Gateway)
* **Технология:** Тонкий прокси-слой (на базе Envoy или Nginx).
* **Назначение:** Принимает весь внешний трафик (от Рекламодателей, Администраторов, Пользователей и DSP-партнеров).
* **Функционал:** Аутентификация, Rate Limiting (защита от DDoS/DDoS-атак со стороны DSP), распределение запросов по внутренним микросервисам и реализация паттерна *Circuit Breaker* для изоляции отказов.

### 2.2. Горячий контур (Hot Path) — Stakes Service Domain
Самый критичный узел системы, отвечающий за генерацию выручки. Чтобы удержать **SLO P95 < 80 мс при 50 000+ RPS**, компоненты объединены:
* **AD Service API & Auction Engine:** Физически объединены в рамках одного домена (Stakes Service), что устраняет сетевые задержки (network hops) на IPC/RPC взаимодействие.
* **Стек:** Реализован на C++ / Go с использованием асинхронного неблокирующего ввода-вывода (модель Event Loop на системных вызовах `epoll`).
* **Кэширование (Cache-Aside):** Сервис вообще не ходит в реляционную БД во время аукциона. Настройки кампаний и лимиты ставок читаются из **In-Memory БД Redis** со временем отклика < 2 мс.
* **Асинхронный прогрев кэша:** При изменении кампании в админке, событие летит в Шину данных (Apache Kafka), откуда Stakes Service асинхронно вычитывает его и инвалидирует кэш в Redis.

### 2.3. Холодный контур (Cold Path) и управление бюджетами
* **Financial Service API:** Изолированный микросервис (на Go), управляющий балансами рекламодателей. Работает со своей выделенной БД (`Financial Service PG`). Здесь исключены асинхронные очереди для критических транзакций, чтобы гарантировать **ACID** и избежать перекрута бюджетов.
* **Advertiser Dashboard API:** Сервис для личного кабинета рекламодателей (Node.js). Занимается CRUD-операциями над кампаниями.
* **Delivery Service API:** Отвечает за формирование HTML/JS-рендеринга баннеров для конечных пользователей сайта.

### 2.4. Аналитика, статистика и работа с данными (OLAP)
Для защиты транзакционных баз данных от тяжелых выборок, аналитический контур полностью отделен:
* **Шина данных (Apache Kafka):** Центр обмена событиями. Сюда со скоростью терабайтов в сутки сливаются сырые логи кликов и показов из `Delivery Service` и `Stakes Service`.
* **Statistics Service & База данных статистики:** Пакетный сборщик (Kafka Connect) выгребает логи из Кафки и пачками (batch insert) складывает их в выделенную базу статистики. Это исключает нагрузку на запись в мастер-БД.
* **Analytics Service API & Analytics Service DB:** Выделенный сервис на Python для тяжелых расчетов и отчетов. Работает на базе read-реплик или колоночной БД, полностью изолируя аналитическую нагрузку от бизнес-транзакций.

## 3. Обоснование границ сервисов и изоляция данных (Database-per-Service)
Каждый микросервис владеет своей базой данных PostgreSQL (или Redis), доступ к которой извне возможен **строго через API** этого сервиса:
1. **Advertiser DB:** Только настройки кампаний и профили.
2. **Financial DB:** Только балансы, счета и транзакции (высокий уровень изоляции для Точности данных).
3. **AD Service DB:** Исторические данные о кандидатах в рекламу.
4. **Кэш Redis:** Только оперативные данные для аукциона в реальном времени.

## 4. Как целевая архитектура решает бизнес-цели (Соответствие Drivers.md)
1. **Масштабируемость и Скорость (Приоритет №1):** За счет выноса аукциона в Stateless-серверы с Redis и `epoll`, система способна линейно масштабироваться под 50k+ RPS в облаке. Тяжелые дисковые операции убраны из Hot Path.
2. **Точность (Приоритет №2):** Выделение `Financial Service` со строгой ACID-базой гарантирует защиту от double-spending, при этом его возможная деградация не останавливает показ рекламы (благодаря кэшированию лимитов в Redis).
3. **Стоимость и Поддержка (Приоритет №3):** Архитектура не переусложнена (всего 6 основных сервисов). Использование управляемых облачных решений (Managed Kafka, Managed PostgreSQL, Cloud K8s) позволяет команде из 35 человек без выделенных SRE успешно эксплуатировать платформу.
