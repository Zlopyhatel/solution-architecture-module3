# Лабораторная работа 1. Архитектурная диагностика и целевое видение платформы AdScale

## Общее описание проекта
Проект посвящен архитектурной эволюции высоконагруженной рекламной платформы AdScale (аукцион RTB, интеграция с DSP-площадками). 
Текущая монолитная система уперлась в потолок производительности при нагрузке 15 000 RPS. 
Цель работы — провести аудит системы, зафиксировать требования и спроектировать целевую отказоустойчивую микросервисную архитектуру, способную выдерживать нагрузку в 50 000 RPS через 1 год с уровнем доступности SLA 99.9%.

## Структура артефактов задания

В данной директории подготовлен полный пакет архитектурной документации:

1. **[README.md](README.md)** — текущий навигационный файл с описанием проекта.
2. **[AS-IS.md](AS-IS.md)** — детальный анализ и диагностика текущей монолитной архитектуры, описание узких мест (Bottlenecks), точек отказа (SPOF) и причин деградации перцентиля P95 времени отклика.
3. **[Drivers.md](Drivers.md)** — архитектурные драйверы системы: функциональные требования (FR), измеримые нефункциональные требования (NFR / Атрибуты качества) по производительности, 
надежности (SLA, RTO, RPO) и масштабируемости, а также бизнес- и технические ограничения (Constraints) с учетом ресурсов команды.
4. **[TO-BE.md](TO-BE.md)** — описание целевого видения системы через 1 год. Включает в себя обоснование стратегии постепенной декомпозиции и применения паттерна Strangler Fig вместо радикальной перестройки системы.
5. **[Diagrams/](Diagrams/)** — директория с архитектурными схемами. Содержит исходный код и визуализацию **C4 Container Diagram (Level 2)** для целевой микросервисной архитектуры через год, 
реализующей подходы CQRS, Database-per-Service и асинхронный I/O.
6. **[adr/ADR-002.md](adr/ADR-002.md)** — Architecture Decision Record. Документ архитектурного решения, фиксирующий и обосновывающий выделение объединенного Сервиса Ставок (Stakes/Bidding Service) 
в качестве первого и самого критического приоритета декомпозиции.

## Ключевые инженерные решения в целевой архитектуре (TO-BE)
* **Изоляция доменов:** Переход на концепцию Database-per-Service для устранения взаимного влияния разнородных типов нагрузок на СУБД.
* **Оптимизация Hot Path:** Вынесение торгов в Stakes Service, внедрение асинхронного неблокирующего ввода-вывода (Async I/O) и In-Memory кэширования (Redis) для снижения задержек P95 ниже 100 ms при 50 000 RPS.
* **Амортизация записи:** Использование распределенной шины данных (Apache Kafka) для асинхронного сглаживания пиков при логировании миллионов событий кликов и показов.
