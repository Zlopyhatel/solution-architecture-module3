# ADR-002. Выделение сервиса ставок (Binding Service Domain) в качестве первого приоритета декомпозиции

## Статус
Принято (Accepted)

## Контекст (Context)
В связи с планами по выходу на международный рынок и интеграции с новыми партнерами, текущая монолитная платформа AdScale перестала удовлетворять нефункциональным требованиям (NFR):
* Текущая нагрузка: 15 000 RPS в пиках. При подключении новых партнеров ожидается рост до 50 000+ RPS.
* Задержки (Latency): Текущий P95 составляет 110–120 мс, при жестком требовании новых партнеров **P95 < 80 мс**.
* Наблюдается периодическая деградация в часы пик из-за блокировок на уровне единой базы данных (Shared Database).
* Отсутствует запас по масштабированию (нагрузка уперлась в потолок производительности монолита).

## Рассмотренные альтернативы (Options Considered)

### Вариант 1: Оставить аукцион внутри монолита, оптимизировав SQL-запросы и индексы
* **Плюсы:** Минимальная стоимость изменений в коде.
* **Минусы:** Не решает проблему contention (конкуренции за ресурсы) на уровне CPU и общей БД. При 50 000 RPS этот подход не позволит удержать P95 < 80 мс.

### Вариант 2: Начать декомпозицию с менее нагруженного сервиса (например, Advertiser Dashboard)
* **Плюсы:** Низкие риски, возможность «обкатать» процессы CI/CD и инфраструктуру микросервисов на простом домене.
* **Минусы:** Не решает главную бизнес-проблему. Сроки интеграции с новыми партнерами будут сорваны, так как критический узел (Hot Path) останется деградировать в монолите.

### Вариант 3: Выделение объединенного Сервиса ставок (Binding Service Domain), включающего AD Service API и Auction Engine
* **Плюсы:** Прямое влияние на ключевую метрику бизнеса (Latency P95). Совмещение API и движка аукциона в один процесс устраняет сетевой оверхед.
* **Минусы:** Высокая сложность и риски при миграции «на живую».

## Решение (Decision)
Принят **Вариант 3**. Выделение сервиса ставок производится по паттерну Strangler Fig через API Gateway в три этапа:
1. **Изоляция домена:** Объединение `AD Service API` и `Auction Engine` в единый сервис (Binding Service Domain) для исключения сетевых задержек (network hops) между ними.
2. **Переход на In-Memory (Cache-Aside):** Перевод чтения настроек кампаний и таргетингов со старой реляционной БД на локальный Redis. Инвалидация кэша реализуется асинхронно через Apache Kafka.
3. **Database per Service:** Выделение изолированной БД PostgreSQL для финансовых и административных данных сервиса, полностью исключающее влияние тяжелых аналитических запросов монолита на Hot Path аукциона.

## Обоснование (Rationale)
1. **Выполнение SLO по Latency:** Объединение API и Auction Engine позволяет выполнять расчет аукциона в рамках одного процесса (In-Memory). 
Использование асинхронного неблокирующего I/O (`epoll`) гарантирует удержание P95 < 80 мс даже при росте нагрузки до 50 000 RPS.
2. **Изоляция отказов (Fault Isolation):** Выделение Binding Service в автономный контур защищает основной бизнес-процесс (показ рекламы и генерацию выручки) от сбоев в других частях системы (например, при падении админки или перегрузке финансового блока).
3. **Фокус ресурсов:** Команда из 35 человек без выделенных SRE не может параллельно распиливать весь монолит. 
Выделение Binding Service как топ-1 приоритета позволяет сфокусировать инженерные ресурсы на самом критичном для выживания бизнеса узле.

## Последствия и компромиссы (Consequences / Trade-offs)

### Плюсы (Pros):
* **Производительность:** Достигается целевой показатель P95 < 80 мс за счет ухода от дискового I/O в сторону In-Memory вычислений (Redis).
* **Горизонтальное масштабирование:** Сервис ставок становится stateless и может линейно масштабироваться в облаке (Cloud-native) независимо от монолита.
* **Разгрузка мастер-БД:** Потоки чтения логов и кликов полностью уходят из центральной БД в Apache Kafka, ликвидируя блокировки таблиц.

### Минусы / Риски (Cons):
* **Усложнение инфраструктуры:** Появляются новые компоненты (API Gateway, Redis, Apache Kafka), требующие мониторинга и поддержки.
* **Повышение когнитивной нагрузки:** Команде из 35 человек придется поддерживать распределенную систему. Для минимизации этого риска инфраструктура разворачивается в управляемой облачной среде (Managed Services).
* **Сложность отладки (Debugging):** Асинхронная модель ввода-вывода и событийная инвалидация кэша усложняют трассировку запросов (требуется внедрение OpenTelemetry / Jaeger на следующих этапах).
