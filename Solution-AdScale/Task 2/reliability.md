# 4. Паттерны надёжности и отказоустойчивости (api-gateway.md / bidding-service.md)

## 4.1. Идемпотентность финансовых операций

* **Генерация уникального идентификатора (Idempotency Key):** 
В момент завершения аукциона Binding Service генерирует уникальный ID (UUID/сквозной ключ), который передается в составе сообщения через Кафку в сервис Financial Service,
который на основании его делает списание средств из бюджета кампании.

* **Механизм защиты на стороне Financial Service (Idempotent Consumer):**
Financial Service вычитывает Кафку и на своей стороне пытается добавить запись в БД. При попытке повторного использования UUID аукциона МС получит отказ БД и повторно запись добавлена не будет.
Для этого на уровне таблицы транзакций в PostgreSQL на поле bidding_uuid настраивается ограничение уникальности (Unique Constraint), которое аппаратно блокирует вставку дублирующих записей.

* **Второй эшелон защиты (Периодическая сверка / Reconciliation):**
Несмотря на описанный выше механизм защиты, периодически могут накапливаться ошибки и расхождения между МС Binding Service и Financial Service.
Чтобы избежать такого сценария, раз в день проводится встречная сверка таблиц МСов по проведенным аукционам в Binding Service и фактическим списаниям в Financial Service.
При возникновении расхождения формируется алерт и отправляется на почту в саппорт для ручного разбора.

## 4.2. Повторные попытки (Retry) с экспоненциальной задержкой (Exponential Backoff)

* **Стратегия повторных попыток на Hot Path (Горячий контур):**
  На "горячем пути" взаимодействия API Gateway ➡️ Binding Service при обработке аукционов (50 000 RPS) использование повторных попыток (Retries) и тем более экспоненциальных задержек (Backoff) полностью **исключено**. 
  
  Причины отказа от повторов:
  1. **Нарушение SLO:** Любое ожидание или повторный запрос не позволят уложиться в жесткий лимит времени P95 < 80 мс, запрос для DSP все равно станет неактуальным.
  2. **Защита от шторма повторов (Retry Storm):** При высокой нагрузке мгновенные повторные запросы со стороны API Gateway лавинообразно умножат входящий RPS, что приведет к каскадному падению Binding Service.
  
  При возникновении сетевой ошибки или таймаута на шлюзе, запрос НЕ повторяется, а система мгновенно переходит к резервной стратегии (Fallback).

* **Применение Exponential Backoff на Cold Path (Холодный контур):**
  Паттерн повторов с экспоненциальной задержкой применяется исключительно во вне-аукционном контуре.
  Например, если Financial Service временно не может обработать событие списания денег из Kafka из-за блокировки БД, он осуществляет повторные попытки с нарастающей паузой (1с -> 2с -> 4с),
  что безопасно для бизнеса и не влияет на скорость показа рекламы.
  
## 4.3. Резервные стратегии (Fallback / Дефолтные ставки)

* **Поведение системы при отказе или недоступности кэша (Redis):**
  Прямое переключение горячего контура (50 000 RPS) на чтение реплик реляционной БД PostgreSQL полностью исключено, так как это приведёт к лавинообразному отказу дисковой подсистемы и деградации Latency.
  Вместо этого применяется стратегия **In-Memory Local Fallback** (локальный аварийный план).

* **Механизм реализации локального Fallback:**
  В локальную оперативную память (RAM) каждого инстанса Binding Service при старте кэшируется статическая заглушечная кампания (например, собственная промо-реклама AdScale или фиксированный контракт)
  с минимальной базовой ставкой (Floor Price). 
  
  При обнаружении недоступности Redis, движок аукциона мгновенно переключается на этот локальный массив данных. Запрос обрабатывается внутри процесса без сетевых ходов (`O(1)` в памяти).

* **Бизнес-эффект:**
  Система сохраняет статус доступности для внешних DSP-партнёров, выполняет требования SLO по времени отклика и предотвращает автоматические блокировки нашей платформы.
  Бизнес минимизирует упущенную выгоду за счёт прокрутки гарантированного пула объявлений, избегая каскадного падения инфраструктуры.
