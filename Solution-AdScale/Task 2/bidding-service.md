
## Спецификация: Выделение RTB-сервиса ставок (Stakes Service)
## 1. Границы сервиса (Bounded Context)

* В зону ответственности сервиса входит:
Со стороны компонента AD Service:
1. Прием HTTP-запросов от DSP-площадки (bid requests); 
2. Определение пользователя; 
3. Подбир кандидатов в рекламу;
Со стороны компонента Auction Engine:
1. Взвешивание ставок;
2. Хранение и применение бизнес-правил; 
3. Расчёт победителя аукциона.
* В зону ответственности сервиса НЕ входит:
1. Управление балансами и списание денег;
2. Хранение сырых логов кликов и показов;
3. CRUD-операции над кампаниями.

## 2. Модель данных (Data Model)

* Структура данных в Redis (для Hot Path):
Индексы (SET): 
target:city:{city_name} и target:interest:{interest_name} — хранят списки ID активных кампаний для поиска пересечения таргетингов.
Объекты (HASH): 
campaign:{campaign_id} — хранит конечные параметры для аукциона (цена bid, ссылка banner_url, статус).

* Таблица campaign (Кампания) 
Поля:
id                (PK)
advertiser_id 		(ID кампании)
bid 				      (Ставка)
advertiser_budget	(Бюджет кампании)
target_city 		  (Город для таргетинга)
target_interests 	(Интересы)
banner_url 			  (Ссылка на баннер)
is_active 			  (Активность / Модерация)

## 3. Внешние зависимости и интеграции (Dependencies)

* Зависимость от API Gateway:
AD Service API получает запросы от DSP-площадки (bid requests). При отсутствии запросов работа блокируется, так как нет новых данных для аукционов.
Тип взаимодействия: синхронно.
При сбое: работа Hot Path полностью блокируется. Платформа переходит в режим ожидания трафика.

* Зависимость от Financial Service: 
Сервис предоставляет информацию по имеющемуся бюджету рекламодателя.
Тип взаимодействия: асинхронно, через шину данных.
При сбое: Сервис ставок продолжает работу на кэшированных в Redis лимитах. 
Для защиты от критического перекрута бюджетов (overspending) вводится временной лимит: если Financial Service недоступен более 5 минут,
сервис ставок автоматически останавливает аукционы для предотвращения прямых финансовых потерь.

* Зависимость от Advertiser / Campaign Service: 
Новые кампании и ставки для аукционов вносятся вручную в Advertiser Dashboard. 
Тип взаимодействия: асинхронно, через шину данных.
При сбое: сервис ставок продолжает бесперебойную работу в штатном режиме на текущих данных из Redis. 
Бизнес-процесс аукциона не останавливается, так как заморожено только создание/изменение кампаний.

## 4. Спецификация API (Интерфейсы взаимодействия)
## 4.1. Внешний интерфейс (Входной запрос от DSP-площадки)
* Метод: POST
* Входные параметры (Request):
1. app_id - ИД площадки;
2. imp_id - ID баннерного места на странице;
3. target_city - город ресурса;
4. target_interest - ключевые интересы ресурса.
* Выходные параметры (Response):
bid_price - ставка победившей кампании;
banner_url - ссылка на рекламный баннер;

## 4.2. Интерфейс приема обновлений бюджетов из шины данных (Kafka Topic)
* Событие: CampaignBudgetUpdated
* Поля сообщения: 
compaign_id 		(ID кампании)
advertiser_budget	(Бюджет кампании)
is_active 			(Активность / Модерация)
