## Спецификация: API Gateway для DSP-интеграции

## 1. Механизм Аутентификации (Authentication)

* **Выбранный метод:** Статический API-key (Токен) в HTTP-заголовке запроса (`X-AdScale-Auth`), валидируемый локально в оперативной памяти API Gateway.
* **Обоснование:** Чтобы исключить сетевые задержки (network hops) и нагрузку на базы данных при 50 000 RPS, список разрешенных токенов DSP-партнеров загружается в локальную хэш-таблицу (In-Memory Map)
* шлюза API Gateway при старте или через динамический конфиг. Проверка входящего запроса сводится к поиску строки в памяти шлюза, что занимает наносекунды (сложность O(1)) и не создает оверхеда на CPU.
* При изменении или добавлении партнеров конфигурация шлюза обновляется без перезагрузки (Hot Reload).
* **Трейд-офф (Компромисс):** Мы осознанно отказываемся от динамических сессий, OAuth-серверов и частой ротации ключей ради максимальной пропускной способности.
* Безопасность этого подхода гарантируется тем, что ключи передаются внутри зашифрованного HTTPS-трафика, а также дополнительно фильтруются на сетевом уровне (по возможности — по диапазонам IP-адресов подсетей партнеров).

## 2. Ограничение частоты запросов (Rate Limiting)

* **Алгоритм Rate Limiting:** Token Bucket (Корзина токенов), встроенный на уровне движка API Gateway.
* **Хранилище счетчиков трафика:** Локальная оперативная память каждого инстанса API Gateway.
* **Обоснование:** Чтобы избежать накладных расходов на сетевые запросы во внешние базы данных при 50 000 RPS, лимиты считаются локально в памяти шлюза.
* Алгоритм Token Bucket выбран потому, что он позволяет сглаживать трафик, но сохраняет краткосрочную гибкость для легитимных микро-всплесков со стороны DSP-партнеров.
* Для отказоустойчивости (при работе нескольких реплик шлюза за балансировщиком) согласованный с партнером лимит RPS пропорционально распределяется между узлами API Gateway.
* **Действие при превышении лимита:** 
  1. Шлюз мгновенно отсекает избыточные запросы, возвращая партнеру HTTP-статус `429 Too Many Requests`.
  2. Включается "предохранитель" (Cool Down) — блокировка накладывается по фиксированному таймеру со смещением (без прогрессивного увеличения штрафного времени), чтобы не усугублять деградацию трафика.
  3. Автоматически генерируется критический алерт (Prometheus Alertmanager) в систему мониторинга нашей команды поддержки и отправляется вебхук саппорту партнера. 
  Это позволяет оперативно валидировать аномалию (DDoS-атака или легитимный рост трафика) и инициировать коммерческий апгрейд лимитов.

## 3. Паттерн автоматического размыкателя (Circuit Breaker)

* **Где размещается Circuit Breaker:** На уровне API Gateway (внешний предохранитель на базе Envoy/Nginx).
* Это позволяет полностью защитить Stakes/Bidding Service от эффекта «грохочущего стада» (Thundering Herd) и дать ему время на восстановление без утилизации CPU на обработку заведомо деградировавшего трафика.
* **Критерии размыкания цепи (Триггеры аварии):**
  * **Порог по Latency (Таймаут):** 40 мс. Если Bidding Service не отвечает за это время, шлюз разрывает соединение.
  * Ожидание свыше 40 мс бессмысленно, так как итоговый ответ с учетом сети не уложится в клиентское SLO (P95 < 80 мс).
  * **Процент ошибок (Error Rate):** > 10% неотвеченных или упавших запросов в рамках скользящего окна в 10 секунд.
  * Данный порог исключает ложные срабатывания от случайных сетевых флуктуаций в облаке, но мгновенно реагирует на системный сбой.
* **Поведение шлюза при разомкнутой цепи (Fallback-ответ):**
* Шлюз прекращает маршрутизацию трафика во внутренний контур и мгновенно возвращает DSP-площадкам легитимный пустой ответ со статусом **HTTP 204 No Content**.
* Это предотвращает автоматическую блокировку нашей платформы со стороны защитных систем DSP-партнеров и позволяет сохранить статус "живой" системы в экосистеме OpenRTB во время внутренней аварии.

## 4. Мониторинг времени отклика (Observability)

* **Инструменты сборки и визуализации:** Экспорт метрик из API Gateway (Envoy/Nginx) в формате Prometheus и визуализация на дашбордах в Grafana.
* **Критические метрики для контроля SLO (Golden Signals):**
  1. **Трафик (Throughput / RPS):** Общее количество входящих bid-запросов в секунду с разбивкой по DSP-площадкам для контроля контрактных лимитов.
  2. **Уровень ошибок (Error Rate):** Мониторинг кодов ответов. Особый фокус на росте статусов HTTP 429 (срабатывание Rate Limiting) и HTTP 204 (срабатывание Circuit Breaker) для мгновенного детектирования аварий.
  3. **Задержка (Latency Перцентили):** Контроль времени обработки запросов на шлюзе. Главный бизнес-показатель — удержание метрики **P95 Latency < 45 мс** для внутреннего контура, что гарантирует выполнение внешнего SLO P95 < 80 мс с учетом сетевого оверхеда до партнеров.
