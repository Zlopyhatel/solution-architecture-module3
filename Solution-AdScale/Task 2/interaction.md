## Спецификация: Проектирование взаимодействия и отказоустойчивости (AdScale)
## 1. Протокол внешнего взаимодействия (Интеграция с DSP-площадками)

* Выбранный протокол:  стандартный протокол OpenRTB (Open Real-Time Bidding)
* Обоснование выбора:
* С точки зрения совместимости с внешними партнерами: так как протокол является стандартом области, для максимальной совместимости решено использовать его
   * С точки зрения Latency (времени отклика): 
   OpenRTB работает поверх протокола HTTP (POST-запросы), где минимальная задержка обеспечивается за счет постоянных открытых соединений (HTTP Keep-Alive / Connection Pooling) между нами и DSP. 
   Это исключает накладные расходы на TCP-handshake для каждого запроса. 
   Сам payload представляет собой плоский, компактный JSON, оптимизированный для сверхбыстрой сериализации и парсинга на уровне нашего высокопроизводительного API Gateway и Stakes Service.

## 2. Протоколы внутреннего взаимодействия (Communication Matrix)

* **Связка: API Gateway ➡️ Bidding Service (Передача входящих bid-запросов)**
  * **Протокол/Инструмент:** Синхронный gRPC (HTTP/2) + Protobuf.
  * **Обоснование:** На "горячем пути" (Hot Path) критически важен Request-Response в реальном времени.
  * gRPC обеспечивает минимальный Latency за счет бинарного формата Protobuf и мультиплексирования запросов в одном TCP-соединении, что предотвращает нехватку портов (connection starvation) при 50 000 RPS.

* **Связка: Financial Service ➡️ Bidding Service (Синхронизация лимитов бюджетов)**
  * **Протокол/Инструмент:** Асинхронный (Apache Kafka + Protobuf).
  * **Обоснование:** Финансовый сервис отправляет событие изменения баланса в шину данных, а Bidding Service асинхронно обновляет оперативную память Redis, изолируя Hot Path от нагрузок на транзакционную БД биллинга.

* **Связка: Bidding Service ➡️ Financial Service (Отправка логов показов рекламы)**
  * **Протокол/Инструмент:** Асинхронный (Apache Kafka + Protobuf).
  * **Обоснование:** Bidding Service после успешного аукциона бросает событие о показе в шину. Финансовый сервис постепенно вычитывает сообщения и списывает деньги, гарантируя ACID без замедления работы аукциона.

* **Связка: Bidding/Delivery Service ➡️ Statistics Service (Сбор сырых логов кликов и показов)**
  * **Протокол/Инструмент:** Асинхронный (Apache Kafka + Protobuf).
  * **Обоснование:** Позволяет убрать дисковую нагрузку (I/O) с сервисов отображения рекламы. Миллионы логов асинхронно сливаются в буфер Kafka для последующей пакетной вставки (batch insert) в базу статистики.

## 3. Архитектурное обоснование выбора технологий

## 3.1. Почему gRPC или REST для Bidding и Campaign?
* Для Bidding (Высокая нагрузка): главным критерием является производительность и низкая задержка.
* Для соблюдения этих требований оптимально использовать протокол gRPC.
* Бинарный формат Protobuf тратит меньше CPU на сериализацию, а поддержка HTTP/2 (мультиплексирование) позволяет обрабатывать 50 000 RPS внутри минимального количества TCP-соединений,
* полностью исключая риск исчерпания дескрипторов файлов (connection starvation) на сервере.
* Для Campaign (Низкая нагрузка): критерием является удобство интеграции, отладки и поддержки работы. Для соблюдения этих требований оптимально использовать протокол REST/JSON.

## 3.2. Почему Apache Kafka для потока событий (Клики/Показы)?

* **Амортизация нагрузки (Backpressure):** В пиковые часы наплыва трафика Kafka выступает в роли защитного буфера.
* Она принимает терабайты сырых логов со скоростью Hot Path, изолируя аналитические базы данных от каскадного падения при резких скачках RPS.
* **Оптимизация дискового ввода-вывода (Batching):** Прямая поштучная запись миллионов событий в секунду убьет любую БД по IOPS.
* Использование Kafka позволяет сервисам-потребителям вычитывать логи пачками (Batch Insert), что минимизирует нагрузку на дисковую подсистему хранилищ.
* **Многократное потребление (Pub/Sub модель):** Одно и то же событие показа рекламы из Кафки могут параллельно и независимо вычитывать разные системы
* (биллинг — для списания денег, антифрод — для валидации кликов, ML — для обучения моделей), не создавая дополнительной нагрузки на работающий аукцион.

## 4. Точка входа: API Gateway

* **Необходимость API Gateway:** Да. Необходим как единая точка входа для изоляции внутренней сети микросервисов от внешнего мира и реализации паттерна Strangler Fig.
* **Архитектурный тип / Технология:** Тонкий и производительный прокси-слой на базе готового индустриального решения (Nginx / Envoy). 
* **Обоснование выбора:** С учетом жесткого ограничения команды (35 человек, отсутствие выделенных SRE) внедрение «умного» или самописного шлюза исключено из-за высоких операционных затрат.
* Выбран «тупой», легковесный и максимально живучий прокси, который не тратит ресурсы CPU на бизнес-логику и гарантированно выдерживает 50 000+ RPS.
* **Критические функции на API Gateway:**
  1. **Терминация TLS/SSL и Аутентификация:** Проверка подлинности запросов от DSP-площадок на самом входе, чтобы не пускать «мусорный» трафик во внутренний контур.
  2. **Rate Limiting & DDoS Protection:** Ограничение максимального количества запросов от каждого партнера для защиты системы от перегрузки.
  3. **Тонкая маршрутизация (Reverse Proxy):** Перенаправление запросов на конкретные микросервисы (внешний OpenRTB — на Bidding Service по gRPC, запросы в личный кабинет — на Advertiser Dashboard).
