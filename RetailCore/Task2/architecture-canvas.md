# Software Architecture Canvas — RetailCore (Текущее состояние AS-IS по стандарту arc42)

## 1. Value Proposition (Бизнес-ценность и экономические драйверы)
*   **Драйверы изменений:** Необходимость кратного масштабирования платформы RetailCore, запуск e-commerce экосистемы и быстрое подключение новых B2B-партнеров/маркетплейсов.
*   **Текущая бизнес-боль:** Низкая скорость изменений (Time-to-Market) и высокие операционные затраты (OpEx) службы поддержки на ручной разбор ошибок.

## 2. Key Stakeholders (Ключевые участники)
*   **Дмитрий (Директор по цифровым продажам):** Бизнес-заказчик и спонсор. Требует роста стабильности Checkout, прозрачности цифр отчетности и сокращения TTM.
*   **Ольга (Head of Support):** Операционный заказчик. Требует единого источника правды в карточке заказа, снижения MTTR и автоматизации нелинейных сценариев.
*   **Андрей (Техлид ядра) / Ирина (Логистика) / Максим (Аналитика):** Технические владельцы и потребители легаси-контура.

## 3. Business Context (Бизнес-контекст и внешние интерфейсы)
*   **Входные каналы трафика:** Собственные витрины (сайт, мобильные приложения) и внешние B2B-каналы (маркетплейсы), синхронно бьющие в один интерфейс.
*   **Внешние соседние системы:** Платежные провайдеры (Payment Gateways) и внешние транспортные компании (службы доставки).
*   **Суррогатные интеграции:** Сторонние легаси-системы, поставляющие данные в виде CSV-файлов.
*   **Аналитический OLAP-трафик:** Прямые SQL-выборки тяжелой отчетности (скрипты Python) из операционной транзакционной базы данных в обход каких-либо интеграционных шлюзов или выделенных хранилищ.

## 4. Core Functions (Ключевые функции и процессы)
*   **Синхронный Checkout:** Сквозной процесс оформления заказа, включающий расчет базовой стоимости, применение промо-скидок, выбор логистического маршрута и создание платежной сессии в рамках одного блокирующего потока.

## 5. Quality Requirements (Требования к качеству / НФТ)
*   **Availability (Доступность):** Необходимость обеспечения отказоустойчивости core-процесса в пиковые сезонные периоды (Черная пятница) за счет механизмов деградации функций.
*   **Data Consistency (Консистентность):** Обеспечение идентичности статусов во всех каналах коммуникации и стопроцентная идемпотентность финансовых транзакций.
*   **Traceability (Прослеживаемость):** Потребность в сквозном аудит-логе (Audit Trail) и Correlation ID для быстрого расследования инцидентов поддержкой.

## 6. Core Decisions — Good or Bad (Ключевые архитектурные решения)
*   **[BAD] Архитектура "God Object":** Бизнес-логика доменов заказов, промо-механик, платежей и логистики монолитно склеена внутри одного класса `OrderProcessingService`.
*   **[BAD] Интеграция через СУБД (Data Coupling):** Использование антипаттерна "Polling по таблице" (Database-as-a-Queue) для логистов. Внешние сервисы по таймеру опрашивают транзакционные таблицы, превращая Oracle в суррогатную шину обмена.
*   **[BAD] Логика на уровне СУБД (Vendor Lock-in):** Часть критических правил промо-расчетов вынесена в тяжелые хранимые процедуры СУБД Oracle (`legacy_promo_pkg`).
*   **[BAD] Размазывание бизнес-логики (Hardcoded Rules):** Правила маршрутизации логистики (Route Rules) хаотично распределены по трем слоям: Java-код, файлы конфигурации приложения и легаси-таблицы Oracle, что требует релиза кода для изменения маршрутов.
*   **[BAD] Хаос интеграционных контрактов:** Отсутствие единого интеграционного контура со службами доставки. Каждый партнер подключается кастомным способом (синхронный REST, пакетные выгрузки, очереди, промежуточный .NET-сервис), что порождает хаос в поддержке контрактов.
*   **[BAD] Совмещение OLTP и OLAP контуров на уровне СУБД:** Источником данных для операционной аналитики (скрипты Максима) выступает мастер-база Oracle. 
  * *Следствие:* Отсутствие единого источника правды (SSOT) порождает рассинхрон в отчетах маркетинга и финансов.
*   **[BAD] Слепые бизнес-сплиты заказов:** При разделении заказа на логистические цепочки внутри БД отсутствует сквозная прослеживаемость и генерация событий.
  * *Следствие:* Клиент видит агрегированный статус, но служба поддержки Ольги не видит детализации внутренних подзаказов, что увеличивает MTTR при инцидентах.

## 7. Components / Modules (Компоненты и модули текущей системы)
*   **Java-монолит платформы:** Компонент, содержащий класс `OrderProcessingService`, репозитории правил `RouteRuleRepository` и общие сервисы статусов.
*   **Вспомогательные легаси-контуры:** .NET integration service (обработка доставки) и Python analytics jobs (выгрузка отчетов).

## 8. Technologies (Технологический стек)
*   **Backend:** Java (монолитное ядро), .NET (интеграционный сервис), Python (аналитические скрипты выгрузки отчетов).
*   **Database:** Терабайтная СУБД Oracle с активным использованием PL/SQL (процедуры, пакеты, триггеры) на физических серверах (on-premise).

## 9. Risks and Missing Information (Риски, проблемные зоны и пробелы)
*   **Риск каскадных отказов:** Синхронный блокирующий характер вызовов `PaymentGateway` и `DeliveryGateway` при сбоях или Latency внешних API полностью парализует чекаут.
*   **Риск внутреннего DDoS СУБД:** При падении логистов легаси batch-процедуры в бесконечном цикле опрашивают таблицу `RETRY_DELIVERY_QUEUE`, вызывая каскадные Row Locks в Oracle и падение сайта (ошибки 500).
*   **Риск неконсистентности («Заказы-призраки»):** Полное отсутствие транзакционных границ (дефицит `@Transactional` в коде) оставляет в БД битые данные при сбоях на поздних этапах.
*   **Риск генерации дублей и роста OpEx:** Отсутствие механизмов дедупликации и контрактов идемпотентности на стыке синхронного и асинхронного контуров приводит к регулярной генерации дублей заявок в транспортных компаниях и росту ручных операций разбора.
*   **Риск деградации прозрачности (Слепая зона перехода):** Высокий риск «ослепнуть» при трансформации из-за отсутствия актуальной документации по "теневым" обходным маршрутам данных и CSV-выгрузкам сторонних систем.
*   **Метрические пробелы (Gaps):** Отсутствие числовых ориентиров по пиковым нагрузкам (целевой RPS), SLA бизнеса (RTO/RPO), SLA поддержки (FRT/MTTR) и стоимости контакта (CPC).
*   **Риск деградации Checkout аналитической нагрузкой:** В периоды распродаж (Черная Пятница) запуск тяжелых исторических выборок и отчетов в Python-скриптах Максима утилизирует CPU/IOPS мастер-базы, конкурируя с транзакциями оформления заказов.
*   **Риск невыявленных интеграционных зависимостей (Shadow IT):** Наличие скрытого файлового обмена (CSV) и прямых обращений legacy-скриптов к внутренним недокументированным API монолита. Существует критический риск сломать смежные системы при постепенном выводе компонентов монолита из эксплуатации (по паттерну Strangler Fig).
