# План переключения (Cutover Plan) для контура Логистики (Этап 3)

## 1. Цель переключения
Финальный перевод интеграционного потока отправки заказов внешним службам доставки со старой схемы (Батчи в СУБД Oracle) на новую событийную модель (RabbitMQ -> Delivery Integration Service) без остановки приема заказов на сайте.

## 2. Условия запуска (Go/No-Go критерии)
* **Инфраструктура:** Кластер RabbitMQ развернут в проде, пройдены нагрузочные тесты, лимиты памяти настроены.
* **Тестирование:** Успешно завершен этап «Теневого запуска» (Shadow Run), контракты данных проверены в логах, расхождений в Correlation ID не обнаружено.
* **Готовность систем:** На стороне внешних логистов верифицирована поддержка канонических контрактов данных и ключей идемпотентности (Idempotency Key).

## 3. Роли и ответственность
* **Координатор релиза (Скрам-мастер):** Ведение тайминга созвона, фиксация шагов, фасилитация коммуникации.
* **Архитектор:** Контроль соответствия целевой схеме, консультации при аномалиях.
* **Бизнес-заказчик (Дмитрий):** Мониторинг бизнес-метрик (конверсия чекаута) во время переключения.
* **Техлид / Лид разработки (Владелец кнопки No-Go):** Финальный технический аудит. Имеет абсолютное право вето и командует началом процедуры отката при нарушении метрик здоровья системы.

## 4. Пошаговый сценарий переключения (Окно релиза: 02:00 - 04:00)

| Время | Шаг | Ответственный | Техническое действие / Проверка данных |
| :--- | :--- | :--- | :--- |
| **02:00** | Фиксация базы | DBA / Админ | Проверка наполненности legacy-таблицы `RETRY_DELIVERY_QUEUE`. Фиксация остатка «хвостов» (например, 150 заказов). |
| **02:10** | Запуск сервиса | DevOps | Включение микросервиса `Delivery Integration Service` в боевой режим чтения из RabbitMQ. |
| **02:15** | **Включение ТУМБЛЕРА** | Лид разработки | Активация Feature Toggle `use_event_driven_delivery = true` в монолите. Все *новые* заказы начинают лететь в RabbitMQ. |
| **02:20** | Дымовой тест | QA Инженер | Создание 5 тестовых заказов на проме. Проверка: заказы НЕ пишутся в старую таблицу, но успешно проходят через RabbitMQ и долетают до тестовых личных кабинетов логистов. |
| **02:30** | Зачистка хвостов | Разработчик | Старый легаси-батч продолжает работать параллельно ТОЛЬКО для доработки тех 150 заказов, что зависли до 02:15. |
| **03:00** | Отключение легаси | DevOps | Legacy-таблица `RETRY_DELIVERY_QUEUE` полностью опустела. Производится полная остановка и деактивация старого легаси-батча в монолите. |

## 5. Проверки после переключения (Пост-валидация и Наблюдаемость)
Дежурная команда в течение 60 минут непрерывно контролирует следующие дашборды в Grafana:
* **Consumer Lag / Queue Depth (Глубина очереди):** График RabbitMQ должен быть стабильно горизонтальным или стремиться к нулю. Экспоненциальный рост очереди — признак каскадного затыка.
* **Circuit Breaker Status:** Состояние предохранителя должно быть строго `CLOSED` (Закрыт). Переход в статус `OPEN` означает, что мы начали DDoS-ить логистов или неверно маппим контракты.
* **Бизнес-валидация:** Сравнение количества созданных заказов в СУБД Oracle с количеством обработанных сообщений в RabbitMQ и логах логистов. Разница должна быть равна 0.

## 6. Сценарий отката (Rollback Strategy)
* **Триггер отката:** Рост Consumer Lag в RabbitMQ > 500 сообщений в течение 10 минут, либо фиксация потери Correlation ID/данных, либо падение брокера сообщений.
* **Порядок действий при откате:**
  1. Лид разработки командует: *«Откат!»*.
  2. Разработчик мгновенно меняет Feature Toggle `use_event_driven_delivery = false`.
  3. Монолит прекращает слать сообщения в RabbitMQ и возвращается к синхронной записи в legacy-таблицы.
  4. DevOps перезапускает легаси-батч опроса таблиц.
  5. Скрипт сверки данных переносит недошедшие из-за сбоя RabbitMQ заказы из логов монолита обратно в таблицу `RETRY_DELIVERY_QUEUE` для ручной или полуавтоматической доотправки.
