# Дорожная карта (Roadmap) миграции платформы RetailCore

## Общая стратегия
Миграция проводится по принципу минимизации радиуса поражения (Blast Radius) и последовательного снижения когнитивной нагрузки на команды. Исключается параллельное изменение кодовой базы монолита (God Object) разными стримами разработки.

## Этап 1. Изоляция OLAP-трафика (Тактический Quick Win)
* **Цель:** Снять критическую non-functional нагрузку с транзакционной СУБД до начала пиковыйх нагрузок.
* **Что делаем:** Настройка read-only реплики Oracle. Перевод Python-скриптов аналитики (Максим) на реплику.
* **Зависимости:** Нет. Задача выполняется силами DBA и команды аналитики, не затрагивает Java-монолит.
* **Риски:** Отставание репликации в пиковые часы (аналитики видят данные с задержкой в несколько минут). 
* **Критерии завершения (DoD):** На мастер-базе Oracle CPU/IOPS от Python-скриптов равен 0%. Отчеты Максима успешно собираются с реплики.

## Этап 2А. Стабилизация периметра (Внедрение API Gateway)
* **Цель:** Построить фундамент для паттерна Strangler Fig, завести весь входящий трафик на единую точку входа.
* **Что делаем:** Развертывание API Gateway в режиме «сквозного прокси» (Transparent Proxy). Трафик маркетплейсов и фронтенда перенаправляется на шлюз, который просто перекидывает запросы в монолит «как есть».
* **Зависимости:** Успешное завершение Этапа 1.
* **Риски:** Ошибки в конфигурации маршрутизации, проблемы с TLS/HTTPS на стороне шлюза.
* **Критерии завершения (DoD):** 100% входящего трафика идет через API Gateway. Монолит закрыт сетевыми экранами (Firewall) от прямых внешних запросов. Метрики TTM на шлюзе стабильны.

## Этап 2Б. Очистка партнерского трафика (Внедрение ACL)
* **Цель:** Изолировать доменную модель монолита от изменений на стороне маркетплейсов, решить проблему скрытых сплитов заказов для поддержки.
* **Что делаем:** Разработка и внедрение сервиса Anti-Corruption Layer (ACL) за API Gateway. ACL нормализует грязные данные партнеров, обогащает их сквозным Correlation ID для Ольги (саппорт) и передает в монолит.
* **Зависимости:** Успешное завершение Этапа 2А.
* **Риски:** Ошибки маппинга специфических статусов редких маркетплейсов; рост задержки (Latency) на прослойке ACL.
* **Критерии завершения (DoD):** Трафик от маркетплейсов проходит валидацию и трансформацию в ACL. Операторы поддержки видят сквозные статусы подзаказов в админке по Correlation ID.

## Этап 3. Асинхронизация логистического контура (Шина + Delivery Service)
* **Цель:** Ликвидация антипаттерна Database-as-a-Queue, устранение Row Locks в СУБД при падении логистов.
* **Что делаем:** Развертывание RabbitMQ. Модификация монолита (публикация событий). Создание `Delivery Integration Service` с паттерном Circuit Breaker для вызова внешних служб доставки.
* **Зависимости:** Завершение Этапа 2Б (команда монолита освободилась от задач по входящему трафику).
* **Риски:** Падение брокера RabbitMQ, потеря сообщений при отсутствии механизма подтверждений (ACK).
* **Критерии завершения (DoD):** Из монолита полностью удалены легаси-батчи опроса таблиц доставки. При симуляции падения внешнего логиста чекаут продолжает работать, Circuit Breaker корректно размыкает цепь.

## Этап 4. Перевод смежных легаси-систем (.NET Integration)
* **Цель:** Полное и окончательное устранение Data Coupling на уровне операционной БД.
* **Что делаем:** Перевод взаимодействия с .NET-сервисом с таблиц `INT_ORDER_EXPORT` на очереди RabbitMQ, развернутые на Этапе 3.
* **Зависимости:** Успешное завершение Этапа 3.
* **Риски:** Команда .NET-сервиса задерживает релиз со своей стороны (внешняя зависимость).
* **Критерии завершения (DoD):** Таблицы `INT_ORDER_EXPORT` и `RETRY_DELIVERY_QUEUE` в Oracle полностью очищены, заблокированы для записи и готовы к удалению.
