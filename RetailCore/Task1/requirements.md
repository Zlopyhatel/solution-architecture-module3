# Архитектурные требования и ограничения проекта RetailCore

## 1. Функциональные требования (ФТ)
*   **ФТ-1 [Базовый жизненный цикл заказа]:** 
    *    Платформа должна обеспечивать стабильный сквозной процесс оформления, расчета стоимости с учетом промо-механик, выбора доставки и онлайн-оплаты.
*   **ФТ-2 [Интеграция с внешними партнерами]:** 
    *    Обеспечение асинхронного двустороннего взаимодействия с маркетплейсами и внешними транспортными компаниями (через вебхуки/callbacks в слое ACL) для мгновенного получения статусов исполнения в реальном времени взамен пакетных батчей (Batch Exchange).
*   **ФТ-3 [Управление нелинейными сценариями / Unhappy Paths]:** 
    *    Автоматическая обработка отклонений от стандартного сценария. Включает поддержку сущности «Отправление» внутри Агрегата «Заказ» для обеспечения автоматического разделения заказа (Split Shipment), внедрение математического модуля позиционного расчета промо-скидок, а также автоматическую маршрутизацию технических ошибок (Content-Based Routing).
*   **ФТ-4 [Интерфейсы операционного контура поддержки]:** 
    *    Предоставление сотрудникам клиентской поддержки контролируемого софтверного интерфейса (Admin API / Back-office BFF) для безопасного управления сценариями заказов с жестким запретом прямой модификации технических статусов в БД в обход доменной логики.
*   **ФТ-5 [Перспективный вектор развития]:** 
    *    Проектирование гибкого интеграционного слоя (Open API / B2B Gateway) в качестве фундамента для запуска новых сервисов (персонализация, партнерские сценарии, экосистема) через 1 год.

## 2. Архитектурно значимые нефункциональные требования (НФТ)
*   **НФТ-1 (Надежность и доступность / Availability):** 
    *    Core-процесс оформления и оплаты заказа должен обладать высокой отказоустойчивостью в периоды пиковых сезонных нагрузок за счет внедрения механизмов Graceful Degradation (возможность временного отключения второстепенных функций вроде рекомендаций или баланса бонусов ради сохранения стабильности оплаты).
*   **НФТ-2 (Консистентность данных / Data Consistency):** 
    *    Гарантия стопроцентной идемпотентности на приемнике для всех платежных транзакций (исключение двойных списаний). Внедрение паттерна CQRS и выделение сквозного сервиса управления статусами (Order State Service) как единого источника правды (Single Source of Truth) для трансляции идентичных состояний заказа во все каналы в реальном времени.
*   **НФТ-3 (Прослеживаемость и наблюдаемость / Traceability & Observability):** 
    *    Реализация паттерна Event Sourcing (Журнал состояний) для фиксации любых мутаций данных. Внедрение двухуровневой прослеживаемости: абстрагированная хронология статусов для клиентов и детальный аудит-лог (Audit Trail) с обязательным использованием сквозного идентификатора (Correlation ID) для поддержки.

## 3. Технологические ограничения (Constraints)
*   **ОГР-1 (Инфраструктурный контур):** 
    *    Развертывание системы возможно только в on-premise контуре на текущих физических серверах компании; ресурсы близки к пределу, быстрое горизонтальное масштабирование на уровне железа невозможно.
*   **ОГР-2 (Целевой стек и импортозамещение):** 
    *    Архитектура должна быть подготовлена к постепенному эволюционному отказу от СУБД Oracle PL/SQL (хранимые процедуры, триггеры) и зарубежных ИТ-компонентов в течение года.
*   **ОГР-3 (Архитектурная стратегия миграции):** 
    *    Запрет на одномоментную полную замену системы (стратегия "Big Bang"). Трансформация должна проходить по паттерну Strangler Fig strictly через вертикальный вынос изолированных бизнес-сценариев (начиная с маркетплейсов) с возможностью безопасного технического отката. Вынос тяжелой аналитики на изолированную read-only реплику СУБД на первом этапе (Quick Win).

## 4. Архитектурно значимые пробелы в требованиях (Gaps)
*   **ПРОБЕЛ-1 (Бизнес-метрики надежности):** 
    *    Отсутствуют оцифрованные целевые показатели SLA по доступности платформы, SLO, а также допустимые рамки времени восстановления (RTO) и потери данных (RPO) в деньгах. Требуется уточнить у Бизнес-спонсора (Дмитрия).
*   **ПРОБЕЛ-2 (Метрики профиля нагрузки):** 
    *    Отсутствуют точные технические параметры пиковых нагрузок (целевой RPS/TPS, p95/p99 времени отклика), а также лимиты свободных мощностей серверов в ДЦ. Требуется уточнить у Техлида монолита и Команды эксплуатации.
*   **ПРОБЕЛ-3 (Операционные метрики поддержки):** 
    *    Отсутствуют числовые ориентиры текущего SLA поддержки (FRT, MTTR) и финансовые показатели стоимости одного контакта (CPC) для расчета окупаемости (ROI). Требуется уточнить у Руководителя поддержки (Ольги).
*   **ПРОБЕЛ-4 (Планы регионального масштабирования):** 
    *    Отсутствуют параметры географической экспансии бизнеса на год, влияющие на требования к сетевым задержкам (Latency) и автономности региональных узлов. Требуется уточнить у Бизнес-спонсора (Дмитрия).
