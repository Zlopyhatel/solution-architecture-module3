# Проект AdScale: Эволюция архитектуры высоконагруженной AdTech-платформы

## Описание проекта
AdScale — это высоконагруженная рекламная платформа (Highload / AdTech), эволюционирующая из монолита в Cloud-native микросервисную архитектуру по паттерну CQRS и Database-per-Service. 

Проект спроектирован с прицелом на международный рынок и рассчитан на целевую нагрузку **50 000+ RPS** при жестком нефункциональном требовании (NFR) к задержкам: **SLO P95 < 80 мс**.

## Основные архитектурные решения
1. **Изоляция Hot Path:** Сервис ставок (`Binding Service`) объединяет в себе домен рекламы и движок аукциона для исключения сетевых задержек. Работает на асинхронном неблокирующем вводе-выводе (`epoll`) в оперативной памяти.
2. **Event-Driven Кэширование:** Настройки кампаний и лимиты бюджетов персистентно хранятся в выделенном облачном кластере Redis со временем отклика < 2 мс. Инвалидация и прогрев кэша управляются асинхронно через шину данных Apache Kafka (паттерн Cache-Aside).
3. **Изоляция данных (Database per Service):** 
   * `Financial Service` — строго транзакционный PostgreSQL с горизонтальным шардированием по ключу `advertiser_id` (защита от double-spending).
   * `Analytics Service` — колоночное OLAP-хранилище на базе ClickHouse для сверхбыстрого построения отчетов по терабайтам сырых логов.
4. **Умная отказоустойчивость:** Внедрен «тупой» и легкий API Gateway (Nginx/Envoy) с поддержкой Rate Limiting на API-ключах в памяти и паттерном Circuit Breaker. При авариях шлюз мгновенно отсекает трафик и возвращает партнерам пустые ответы `HTTP 204 No Content` для предотвращения блокировок.

## Структура репозитория и артефактов

* `Drivers.md` — функциональные и нефункциональные требования (FR/NFR), приоритизация бизнеса.
* `AS-IS.md` — анализ ограничений исходной монолитной системы.
* `TO-BE.md` — детальное описание целевой микросервисной архитектуры.
* `bidding-service.md` — спецификация выделенного сервиса ставок, его границы, API и модель данных.
* `interaction.md` — матрица внутреннего gRPC/Kafka взаимодействия и диаграмма последовательности (Sequence).
* `api-gateway.md` — дизайн защитных барьеров шлюза и паттерна Circuit Breaker.
* `database-strategy.md` — обоснование выбора СУБД под задачи каждого микросервиса.
* `scaling.md` — стратегии репликации, CQRS и шардирования для международного масштабирования.
* `caching.md` — детальный дизайн кэширования в Redis и алгоритмы прогрева кэша.
* `event-streaming.md` — архитектура брокера Kafka: топики, партиции, группы потребителей и Log Compaction.
* `disaster-recovery.md` — параметры RPO/RTO для разных контуров данных и соответствие принципам 12-Factor Apps.
* `diagrams/` — архитектурные диаграммы (C4 Container, Component, Sequence) в форматах Draw.io и PlantUML.
